# ICSS Bookings audit — 20 October 2026

## Scope and result

Audited the public site, 20 industry previews, shared booking UI, website-builder playground, booking API rules, payment/status transitions, tenant access controls, calendar cancellation, dependency security, and production health. Reproducible defects were fixed and covered by regression tests. This is a bounded functional audit, not a guarantee that every possible input or external-provider failure has been exercised.

## Fixed

- Older saved website documents containing blank logo, tagline, or address placeholders now inherit the previous Booking Page Branding values. New-format documents still respect intentional removals after saving.
- Both cancellation routes and rejection close pending payment records without rewriting already-paid records. The dedicated cancellation route now locks and updates booking/payment state together in one transaction.
- Cancelled, rejected, and expired reservations cannot be reactivated by changing status without reserving a fresh slot. Pending bookings cannot be marked completed/no-show before confirmation.
- Repeated status requests do not resend confirmation/cancellation notifications.
- Status-based cancellation/rejection now calls calendar synchronization. Google/Microsoft deletion clears stale event IDs and treats already-deleted events as successfully removed.
- Approving an after-hours request using a hosted payment link or offline collection now settles the pending payment record, consistent with manual-transfer approval.
- Build information uses the Railway commit SHA when available and avoids shell error output when git is absent from the production image.
- Updated follow-redirects, Vite, and React Router to patched releases. Added frontend dependency auditing to CI and aligned its declared Node requirement with the Node 20 deployment image.

## Verification

- 67 automated tests pass. Coverage includes strict booking terms consent, phone booking attribution/optional email, tenant isolation, read-only impersonation, booking conflicts/capacity, blocked-time explanations, payment requirements, new status regressions, calendar deletion transport behavior, all 20 preset documents, and branding save/reopen behavior.
- Production frontend build passes. ESLint reports zero errors and 11 existing warnings (hook dependencies, fast-refresh exports, unused bindings); warnings were not hidden.
- Backend and frontend npm audits report zero known vulnerabilities at audit time.
- Live browser: all 20 template home pages render; no application console errors observed (browser-extension diagnostics excluded). About/Gallery/Book navigation was exercised on the universal template; required terms checkbox starts unchecked and submission is disabled.
- Live playground: clicking a heading selects its inspector, edits reach the preview, Undo restores the original, clicking a gallery photo selects the correct photo, adding a video section exposes video/cover controls, and Phone mode renders a 390px preview.
- Public landing/legal/FAQ pages and all 11 distinct local asset/page links found in the landing and terms HTML returned HTTP 200. The theme catalogue API and health endpoint return 200. Anonymous requests to account, platform, booking-admin, and summary APIs are denied.
- Railway: one healthy running replica, no crashed replica or failed deployments reported in the preceding 24 hours. Average memory was about 50 MB, peak about 335 MB; CPU use was low during the observation window. This is not a load test.

## Remaining configuration and verification limits

- Production logs report no PayPal subscription plan ID. Subscription signup/billing cannot be certified end to end until the intended PayPal plan is configured and a controlled checkout is performed.
- Google/Microsoft OAuth credentials and the calendar token encryption key are not configured in the observed service. Calendar logic was verified using isolated provider responses, not live connected calendars.
- PAYPAL_JMD_PER_USD is unset; code currently falls back to 160 JMD per USD. The business should explicitly choose its intended conversion rate. No exchange rate or billing configuration was changed during this audit.
- PUBLIC_APP_URL is unset but application links fall back to BASE_URL. PLATFORM_ADMIN_KEY is unset for legacy key-protected provisioning endpoints; authenticated platform-console access uses separate role guards.
- No production customer bookings were created, no customer messages were sent, and no payments were charged. Admin persistence, media upload, email delivery, subscription provisioning, and real payment-provider completion were not exercised with a signed-in production test account.
- API regressions use an isolated HTTP server with database/provider stubs. A local PostgreSQL installation was unavailable in this environment; database migrations and concurrent transaction behavior were not replayed against a fresh database. Production startup/database health was checked through deployment status/logs.
- Authenticated console interactions and every responsive size/browser combination were not manually exercised. Existing lint warnings remain follow-up maintenance work.

## Release verification

The fixes are delivered through the GitHub main branch and Railway's native GitHub source. The deployment's terminal status, commit SHA, public health, and representative browser routes must be checked after the main-branch update; a queued build alone is not proof of deployment.


## Booking invoices and verified reviews added during the audit

- A new Invoices admin section lets tenant admins customize business identity/contact details, PNG/JPG logo, two colours, payment instructions and footer while keeping one fixed A4 layout. Staff can download booking invoices; only tenant admins can edit invoice settings.
- New booking invoices are stored in the booking transaction with a snapshot of the service price, business details, branding, and embedded logo. Existing bookings receive an invoice on first download/email; those older records use the available historical price and current service/branding because no earlier invoice snapshot exists.
- Confirmation, pending payment/review, and completed-booking emails attach the invoice. Phone booking email remains optional; supplying it sends the same details and PDF. Without an email, staff can download the invoice from the dashboard.
- Verified payments and outstanding balance are separate. Deposits do not appear as full payment; pending payments are not counted as paid. A cancelled/rejected invoice directs the customer to the business about settlement/refunds.
- Completed-booking email includes a private, tenant-bound review invitation valid for 180 days. Only completed bookings may submit; repeat submissions update that booking's review. Public output uses first name/last initial, rating, comment, and date, never customer email or booking ID.
- Booking pages show aggregate rating/count and three reviews. See more opens a scrollable, paginated dialog. No tenant directory was added.
- Nine additional HTTP/service tests cover invoice ownership and role restrictions, immutable snapshots, money calculations, PDF email attachment paths, no-email phone bookings, review invitation validation/expiry, duplicate review updates, summary counts, and pagination.
- Sample invoice was rendered with embedded fonts and visually checked as a one-page A4 PDF. Public live review creation and production email delivery are not test-submitted; transport and database interactions are isolated in automated tests.
